# P-060: Execution proof system and proving-machine selection

Status: Implementation draft 0.2  
Protocol version: Development profile 1  
Reference implementation: `p060-execution-proof` 0.1.0  
Supersedes: the “purpose-specific transparent STARK VM” sketch in `PQVM.md`

## 1. Scope and conformance

This document specifies the component that produces and verifies execution-validity proofs for the authoritative state transition: the proof-system security profile, suite registration, public inputs, receipt encoding, verifier contract, resource limits, and the gated process for selecting a proving machine.

P-050 defines what is executed. P-060 defines what proves it. P-111 remains a separate private-relation proof path. P-111 proves that an approved private relation holds; P-060 proves that the public transition function was executed correctly.

The words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

This version defines two conformance levels:

1. **P-060 protocol conformance** requires every normative security, verifier, independent-implementation, resource, and refinement gate in this document.
2. **P-060 Gate-1 reference conformance** implements the suite and verifier contract against the accumulator AIR in §6. It is measurement software. It MUST NOT be represented as a proof of P-050 execution or as consensus-ready.

The included code has Gate-1 reference conformance only. P-050 was not available to this implementation, so the accumulator AIR is an executable stand-in used to validate the architecture and receipt boundary.

## 2. Governing requirement and non-goals

If execution validity is established by proof rather than universal re-execution, the authoritative proof MUST be transparent and hash-based. Pairing-based commitments, KZG, Groth16, and curve-committed PLONK are excluded from the authoritative verification path. A quantum break of such a commitment can become a soundness failure, rather than merely a privacy failure.

This requirement selects a security profile and receipt mode. It does not, by itself, justify a new instruction set.

P-060 does not:

- replace P-050 ObjectVM semantics;
- provide privacy or zero knowledge;
- prove jobs, AI computation, or external evidence;
- establish finality;
- justify a developer-facing general-purpose zkVM; or
- make an unconditional or NIST-certified post-quantum claim.

## 3. Architecture selection

Exactly one architecture MUST be selected before execution proofs become consensus-required.

### 3.1 Option A — existing semantics, transparent STARK

Arithmetize the existing P-050 execution trace using a transparent STARK. Preserve the P-050 interpreter, vectors, verifier, and formal model.

This is the default. It has the lowest correctness and schedule risk. Failure is expected to be a proving-performance problem.

### 3.2 Option B — transparent-only fork of an existing zkVM

Fork a general zkVM, remove every curve-based commitment and compression mode, and pin transparent receipts. This inherits a large audit surface and a permanent upstream-maintenance burden. Recursion may still need to be rebuilt.

### 3.3 Option C — purpose-built machine and AIR

Design an instruction set for cheap arithmetization. This has the greatest potential constant-factor gain and the highest semantic, compiler, audit, formal-method, and schedule cost.

### 3.4 Current decision

Option A is provisionally selected for Gate 1. Options B and C MUST NOT open unless measured Option-A results miss a §10 bound and the proposal accounts for all duplicated P-050 semantics, vectors, verifier work, formal models, and second-client cost.

The included accumulator AIR validates the Option-A integration shape; it does not close Gate 1 because it is not the P-050 AIR.

## 5. Hashing and security profile

### 5.1 Protocol-boundary hash

Every state root, block identifier, program identifier, and vector receipt identifier in this profile uses SHAKE256 with 384 output bits:

```text
BoundaryHash(domain, payload) =
    SHAKE256-384(
        "P060-BOUNDARY-v1\0" ||
        u16be(len(domain)) || domain ||
        u64be(len(payload)) || payload
    )
```

No algebraic or 256-bit digest crosses this protocol boundary.

### 5.2 STARK-internal hash

The development suite uses SHAKE256/384 for Winterfell Merkle commitments and the Fiat–Shamir transcript. Each operation has a distinct ASCII domain:

| Operation | Domain |
|---|---|
| Arbitrary bytes | `P060-WF-HASH-v1\0` |
| Binary Merkle merge | `P060-WF-MERGE2-v1\0` |
| N-ary merge | `P060-WF-MERGEN-v1\0` |
| Digest plus integer | `P060-WF-MERGE-U64-v1\0` |
| Field elements | `P060-WF-ELEMENTS-v1\0` |

Lengths or counts are included where concatenation would otherwise be ambiguous. Field elements use Winterfell’s canonical serialization.

Winterfell 0.13.1 exposes only 32 bytes through `Digest::as_bytes()` to its random coin. The P-060 digest type retains and serializes all 48 bytes for Merkle commitments; the coin consumes the first 32 bytes of each 48-byte result. This limitation is a named suite assumption and MUST be re-evaluated before consensus use.

### 5.3 Soundness claim

For the registered parameters, Winterfell reports:

- **127 bits conjectured security**;
- **77–82 bits proven LDR security** on the measured traces; and
- **53–55 bits proven UDR security** on the measured traces.

The suite’s required 100-bit claim is therefore **conjectured, not proven**. It is conditioned on:

- SHAKE256 preimage and collision resistance, including generic quantum costs;
- Fiat–Shamir soundness in the quantum random-oracle model;
- the conjecture used by Winterfell’s security estimator;
- FRI/DEEP composition soundness;
- correctness of Winterfell 0.13.1 and this adapter; and
- correctness of the AIR refinement to the authoritative semantics.

The 384-bit Merkle output has approximately 192-bit generic classical collision cost and 128-bit generic quantum collision cost. The 256 transcript bits exposed by Winterfell have approximately 128-bit generic quantum preimage cost. These are generic-attack estimates, not proofs of the complete protocol.

If protocol policy requires 100 **proven** bits, suite `0x00060001` is non-conforming and MUST NOT be activated. Parameters MUST be increased or a different registered suite selected.

## 6. Gate-1 accumulator AIR

This AIR is a deliberately small stand-in for P-050. Its sole purpose is to exercise the complete Option-A proving and receipt path.

### 6.1 State and operations

The public state is one canonical Goldilocks field element encoded as a big-endian `u64`. Values greater than or equal to `p` are invalid.

The canonical block contains zero to 1,024 operations:

- opcode 0, `ADD operand`: `next = state + operand` in the field;
- opcode 1, `MUL operand`: `next = state × operand` in the field.

### 6.2 Trace

The trace has three columns:

| Column | Meaning |
|---|---|
| 0 | Current state |
| 1 | Opcode |
| 2 | Operand |

Trace length is `next_power_of_two(max(8, action_count + 1))`. Unused transitions are padded with `ADD 0`.

For each transition, the AIR enforces:

```text
opcode × (opcode - 1) = 0

next_state - [
    (1 - opcode) × (state + operand) +
    opcode × state × operand
] = 0
```

The first and last states are boundary assertions. Every transition row’s opcode and operand, including padding, is a boundary assertion. This makes verification grow linearly with action count and is intentionally a baseline to improve in the real P-050 AIR.

### 6.3 Boundary roots

For this AIR only:

```text
state_root = BoundaryHash("state-root", u64be(state))
block_id   = BoundaryHash("canonical-block", canonical_block_bytes)
```

The receipt header values, public state values, and canonical block are also Fiat–Shamir public inputs. Thus an accepted proof is bound to the program, protocol, verifier, suite, pre-state, exact block, and post-state.

## 7. Canonical encodings

All integers in the outer P-060 encoding are unsigned big-endian. All reserved bytes MUST be zero. Unknown versions, malformed lengths, non-canonical field values, and trailing bytes MUST be rejected.

### 7.1 Canonical block

| Offset | Size | Field |
|---:|---:|---|
| 0 | 8 | ASCII `P060BLK1` |
| 8 | 2 | Codec version, 1 |
| 10 | 2 | Reserved, zero |
| 12 | 4 | Action count |
| 16 | `count × 16` | Action records |

Each action record is:

| Relative offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Opcode |
| 1 | 7 | Reserved, zero |
| 8 | 8 | Canonical field operand |

### 7.2 Receipt

| Offset | Size | Field |
|---:|---:|---|
| 0 | 8 | ASCII `P060RCP1` |
| 8 | 2 | Receipt codec version |
| 10 | 2 | Receipt kind |
| 12 | 4 | Protocol version |
| 16 | 4 | Verifier version |
| 20 | 4 | Suite ID |
| 24 | 4 | Flags, zero |
| 28 | 48 | Program identity |
| 76 | 48 | Pre-state root |
| 124 | 48 | Canonical block ID |
| 172 | 48 | Post-state root |
| 220 | 4 | Public-input-envelope length |
| 224 | 4 | Proof length |
| 228 | variable | Public-input envelope |
| variable | variable | Winterfell proof |

The receipt length MUST equal `228 + public_input_length + proof_length` exactly.

### 7.3 Public-input envelope

| Relative offset | Size | Field |
|---:|---:|---|
| 0 | 8 | ASCII `P060PUB1` |
| 8 | 2 | Codec version, 1 |
| 10 | 2 | Reserved, zero |
| 12 | 8 | Pre-state field element |
| 20 | 8 | Post-state field element |
| 28 | 4 | Canonical-block byte length |
| 32 | variable | Canonical block |

### 7.4 AIR public-element order

The Fiat–Shamir public-element vector is, in order:

1. receipt codec, receipt kind, protocol version, verifier version, suite ID, flags;
2. program ID, pre-state root, block ID, and post-state root, each split into consecutive seven-byte chunks interpreted as little-endian field elements;
3. pre-state, post-state, and action count; and
4. each action’s opcode and operand in block order.

Seven-byte chunks are used so every chunk is canonical in the Goldilocks field.

## 8. Verifier contract

A conforming verifier MUST execute the following order:

1. Reject a receipt larger than 160,000 bytes before decoding nested values.
2. Strictly decode the fixed header and lengths. Reject reserved bits and trailing bytes.
3. Reject an unregistered codec, receipt kind, protocol version, verifier version, suite, or program identity.
4. Strictly decode the public-input envelope and canonical block.
5. Recompute and compare the program ID, pre-state root, block ID, and post-state root.
6. If an expected external context is supplied, compare all six expected bindings before cryptographic verification.
7. Decode the proof within the 131,072-byte cap.
8. Require the exact registered `ProofOptions`, trace width, and trace length. A minimum-security predicate alone is insufficient.
9. Require the reported conjectured security to be at least 100 bits.
10. Construct public elements in the §7.4 order and verify the STARK with the registered AIR and hasher.
11. Return success only if every step succeeds.

All failures are rejection. Underlying deserializer or verifier panics are caught and converted to rejection.

The reference verifier has no unbounded recursion. Allocation-driving receipt, proof, public-input, action, trace, and parameter values are bounded before proof verification. Hardware accelerators have no verifier privilege.

## 9. Determinism and reproducibility

With the pinned `Cargo.lock`, Rust-compatible toolchain, single-threaded Winterfell build, canonical inputs, and registered parameters, the same input produces byte-identical receipts. The test suite proves this property for the positive vector.

The prover MUST NOT depend on time, locale, filesystem ordering, thread scheduling, or accelerator availability. A future parallel or accelerated prover MAY produce different proof bytes only if the registered verifier accepts them and the nondeterminism is documented.

Proof-producing hardware is never a validity authority.

## 10. Resource bounds and Gate-1 measurements

Before proof-authoritative activation, the named reference machine and comparison methodology MUST be protocol-versioned. A light-client verifier MUST run on commodity consumer hardware. Verification of one block MUST NOT cost more than ten times the selected Ethereum consensus light-client-update baseline, and one receipt MUST fit the published mobile bandwidth budget. Recursion, if introduced, inherits every P-060 security requirement.

Development-profile admission bounds are:

| Resource | Bound |
|---|---:|
| Receipt bytes | 160,000 |
| Proof bytes | 131,072 |
| Public-input bytes | 20,000 |
| Actions | 1,024 |
| Trace rows | 2,048 |
| Verifier working-set target | 64 MiB |
| Verification target on reference machine | 250 ms |

Measurements were taken on 2026-07-27 using an Apple M5 Max, macOS arm64, Rust 1.97.1, `cargo build --release`, single-threaded Winterfell 0.13.1:

| Actions | Trace | Prove | Proof | Receipt | Verify mean / max (10 runs) |
|---:|---:|---:|---:|---:|---:|

The Ethereum comparison baseline, sustained throughput workload, and second machine are not yet measured. Therefore §10 does not close Gate 1.

## 11. Selection evidence and decision gates

The current evidence is:

| Criterion | Result |
|---|---|
| Proving cost | 24–589 ms in the sampled 8–2,048-row accumulator traces; peak combined process RSS 144.1 MB |
| Proof size | 4.6–65.6 KB; no recursion |
| Verification cost | 0.24–53.48 ms observed; 4.95 MB max RSS for the max receipt |
| Soundness | 127 bits conjectured; 53–82 bits under published proven estimators |
| Local audit surface | 1,370 physical Rust lines in the library, plus 226 CLI lines and the unowned Winterfell dependency graph |
| Semantic duplication | None measured; the P-050 refinement is not implemented |
| Second-client cost | Not measured; no independent verifier exists |
| Schedule risk | The receipt path is small; P-050 arithmetization remains unknown |

**Gate 1 — feasibility.** Implement and measure the real P-050 AIR. If it meets §10, select Option A and do not pursue B or C.

**Gate 2 — justification.** Open B or C only if Gate 1 misses a bound by a stated margin and the proposal prices all semantic and formal duplication.

**Gate 3 — exit.** If no option meets the bounds by the proof-authoritative milestone, retain re-execution as authoritative validity and defer proof authority to a later protocol version. Security requirements MUST NOT be relaxed to meet a schedule.

## 12. Relationship to re-execution and liveness

Validator re-execution remains authoritative until:

- the real P-050 AIR and refinement claim exist;
- the §10 comparison closes;
- all §13 vectors pass in two independent verifier implementations;
- cryptographic and implementation review completes; and
- prover-unavailability behavior is protocol-defined.

The transition to proof-authoritative validity is a protocol-version change. A block header SHOULD reserve a proof field before activation so a later version does not reinterpret historical bytes.

Prover concentration is a liveness risk even though proving hardware is not a validity authority. Before activation, the protocol MUST define deadlines, fallback behavior, fee handling, and whether blocks without timely proofs can be re-executed or must be rejected.

## 13. Vectors, tests, and independent verification

The reference implementation includes:

- a deterministic positive receipt and canonical block in `vectors/`;
- byte-reproducibility testing;
- negative tests for wrong receipt kind, protocol version, verifier version, suite, program identity, pre-state root, canonical block, post-state root, public input, proof bytes, expected context, reserved bits, malformed lengths, and trailing bytes;
- a valid STARK generated with an unregistered parameter set, which the verifier rejects before cryptographic acceptance; and
- arbitrary-input and malformed-proof panic-containment tests.

Before protocol conformance, the project MUST additionally publish portable negative binary vectors and an independent verifier that reproduces every outcome without importing this verifier or its Winterfell adapter. Until then, the implementation MUST NOT be described as independently verifiable validity.

The required formal statement is a refinement theorem or reviewed claim joining the P-050 transition relation to the AIR. The accumulator AIR has no such claim to P-050.

## 14. Compatibility

Receipt codec, receipt kind, protocol version, verifier version, suite ID, program ID, field, hash, and proof parameters form one registered suite. A later protocol version MAY register a new suite, but MUST NOT reinterpret any receipt accepted under an older suite.

Historical verification MUST retain the exact old decoder, program identity, parameter set, and resource rules. “At least this much security” is not a substitute for exact historical suite dispatch.

## 15. Implementation status and open work

Implemented:

- Option-A transparent STARK proving and verification path;
- SHAKE256/384 boundary and internal hashing;
- exact suite registry and parameter rejection;
- canonical block, public-input, and receipt codecs;
- bounded, panic-containing verifier;
- protocol/public-input binding;
- deterministic vectors, mutation tests, and benchmarks; and
- command-line prove, verify, inspect, vector, and benchmark workflows.

Not implemented and blocking protocol conformance:

- P-050 ObjectVM AIR and refinement evidence;
- independent second verifier;
- 100-bit proven soundness, if policy requires it;
- recursive aggregation, if target blocks require it;
- the Ethereum light-client comparison;
- a second reference machine and sustained-load benchmark;
- formal allocator-level verification of the 64 MiB target;
- prover-unavailability rules; and
- proof-field integration into the actual block header.

Open questions remain whether ObjectVM is arithmetization-friendly, whether recursion is needed at target throughput, whether a younger algebraic hash is acceptable for a future recursive suite, and whether P-111 and P-060 can share a verifier surface without conflating their security roles.
