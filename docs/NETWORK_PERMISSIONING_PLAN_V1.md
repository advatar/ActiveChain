# Network permissioning plan v1

Making "who may run a node" and "who may use the network" configurable when a
network is created, rather than assumptions baked into a testnet.

These are two independent axes and the plan keeps them independent. A network
may be open to users and closed to validators (a public testnet with a fixed
operator set — what Kanalen is today), closed to users and open to validators
(rare, but a consortium's private data plane), or closed to both (the regulated
deployment Track B is heading for). Collapsing them into one "private network"
switch would make the common case unexpressible.

## What already exists

More than the absence of a UI suggests, and the plan is mostly about wiring and
committing rather than inventing.

**User access is built.** `crates/rpc-types` defines `RpcAccessTerms`,
`RpcAccessGrant` and `RpcAccessAuthorization`; `crates/rpc-server/src/access.rs`
enforces them. The mode enum is already `Free | Allowlist | Prepaid`. An
operator signs terms naming the chain, the operator key and the price of each
request class. The operator then signs a grant binding a specific
`client_public_key`, a validity window and a unit allowance. The client signs
every request over a `request_commitment` plus a sequence number, so a captured
authorization cannot be replayed or retargeted at a different request, and
`UsageState` (TYPE_TAG `0x00be`) persists the high-water sequence and spend per
grant across restarts. `Status` and `AnchorServiceStatus` are always free, which
is deliberate — monitoring must not need a grant.

What is missing is not the mechanism but its reach: no field in
`NetworkManifest` selects a mode, the node takes the terms file as a positional
argument that the Kanalen launch agent never passes (so it runs `Free`), the
operator console cannot issue a grant, and **there is no revocation** — a grant
is valid until it expires, whatever happens in between.

**Node participation is closed by construction, not by policy.** The validator
set is fixed at genesis: `ValidatorGenesisEntry { validator, stake, public_key }`,
with keys generated by `genesis-tool` and a `validator_set_root` committed into
`genesis.bin`. Consensus authenticates every proposal and vote against that set,
so an outsider cannot vote. But `PeerListener::bind(("0.0.0.0", port))` accepts
any TCP connection and authenticates at the message layer only, with pre-auth
rate limiting as the sole defence before a signature is checked. The protocol
types carry an epoch (`MAX_VALIDATORS_PER_EPOCH`, `genesis.epoch()`), yet nothing
changes membership after genesis — `settle_epoch_durable` settles economics, not
the validator set. The manifest's whole vocabulary for this is `validators: u8`.

So today: users are unrestricted, validators are unchangeable, and neither is a
decision anyone made per network.

## The decision that drives the rest

Where does admission policy live — in each node's configuration, or committed to
the chain?

Node-local configuration is cheaper and needs no consensus work, but it makes
"permissioned" an operator-by-operator claim. A user refused by one node is
served by the next, and the network cannot state its own membership. That is
acceptable for rate limiting and unacceptable for regulation.

**Recommendation: commit the admission roots to the chain, and let an operator
additionally refuse.** An operator may always be stricter than the network,
never laxer. This is the same shape jurisdiction profiles already use by binding
to assets rather than to networks, and it keeps a single node's misconfiguration
from silently widening access.

## Proposed model

Two registries, each with a root committed at genesis, each epoch-scoped, each
changed only by a threshold — not by whoever holds the machine.

### Node admission

A `NodeAdmissionPolicyV1` in genesis carrying a mode (`Open | Permissioned`) and
an admission root over the admitted node set. A node presents a
`NodeAdmissionCertificateV1` binding its public key, the chain id, a validity
window and a **role**, because these are different rights and a network will
want to grant them separately:

| role | may |
|---|---|
| observer | read via RPC, follow finality |
| full node | the above, plus relay and serve blocks |
| validator | the above, plus propose and vote |

Enforcement lands in two places. Consensus keeps its existing signature check
against the validator set — unchanged, so no consensus risk. The new check is at
the transport: a permissioned network completes a handshake proving possession
of an admitted key before accepting peer traffic, which both enforces membership
and removes the pre-auth flood surface that rate limiting currently absorbs
alone.

Authority to change the set is the trust signer set (`TrustSignerSetV1`,
threshold), not the operator console. The console orchestrates; it does not
sign. That is the same boundary the trust ceremony already defends, and for the
same arithmetic reason.

### User admission

Extend what exists rather than replace it.

- `NetworkManifest` gains an `access` block — mode, unit prices, grant lifetime
  ceiling — which the planner renders into an access-terms file and wires into
  the launch agent, so the mode is a property of the network as created.
- Add `RpcAccessRevocationV1`: a revocation list with its own root, checked in
  `authorize` alongside expiry. Without it, the only way to withdraw access from
  a compromised client key is to rotate the operator key and re-issue every
  grant.
- Commit an **issuer** root to the chain — which keys may sign grants for this
  network — so a grant is network-scoped rather than merely a claim by whichever
  node answered.

`Allowlist` mode then means what its name says today and is deployable in the
first phase with no protocol change.

## Relationship to the regulated track

User admission is exactly where a jurisdiction asks "who is this?", and Track B
already has the unwired pieces — `KenyaRegulatedProfileV1`,
`RegulatedTransferAdmission`, `require_selected_profile`.

Keep the two types separate even though they will often be issued together. A
network access grant answers *may this key call the API*; a regulatory profile
answers *has this person been screened*. Conflating them turns a compliance
lapse into an outage, and makes the access path — which every request touches —
depend on the compliance path's availability. Issue them as distinct
certificates to the same subject, and let a transfer require both.

## Phasing

Sequenced so nothing here blocks getting the testnet usable.

**P0 — configuration only, no protocol change.** Manifest `access` block;
planner renders terms and passes them to the node; console displays the mode and
issues and lists grants; add revocation. Delivers real user permissioning using
machinery that is already written and tested, with zero consensus risk. This is
the phase worth doing soon.

**P1 — node admission as configuration.** Manifest gains a `nodes` block;
`genesis-tool` commits the admission root; the peer handshake refuses
non-members. Still no membership *changes* — the set is what genesis said, which
matches how networks are actually stood up.

**P2 — post-genesis membership changes.** Epoch-scoped admission transitions
authorized by the trust signer set. This is the phase with real consensus work
and it needs its own formal scope before it is written.

## Properties to state, and prove

Following the standard the rest of the estate is held to (see
[#802](https://github.com/advatar/ActiveChain/issues/802) for the existing gap):

- **Admission soundness.** A peer message is accepted only if its signer is in
  the admitted set for that epoch.
- **Role separation.** No certificate of role *observer* or *full node* admits a
  proposal or vote.
- **Revocation effectiveness.** No authorization succeeds against a grant once
  its revocation is in effect, regardless of remaining validity or units.
- **No replay.** Sequence monotonicity per grant — partly enforced today by
  `UsageState`, currently defended by tests.
- **Threshold soundness for admission changes.** No accepted sequence of
  signatures satisfies a threshold of *k* with fewer than *k* distinct signers —
  the same statement the ceremony needs, and worth proving once for both.

## Risks worth naming now

**Lockout is the real hazard.** Every mechanism here is a way to make a network
refuse its own operators. The plan must carry a recovery path — a
threshold-signed admission reset that does not require access to the network
being reset — and P1 should not ship without it.

**Free liveness must stay free.** `Status` and `AnchorServiceStatus` are exempt
today. Keeping that exemption is a requirement, not an oversight: monitoring and
the wallet's reachability check both depend on it.

**A handshake is new attack surface.** P1 introduces peer authentication where
there is none. It should reuse the existing ML-DSA verification path rather than
introduce a second one, and its parser is a natural Kani target.
